# Wigul — 소비 숙려 기반 Android 서비스 백엔드

구매를 결정하기 전, 소비를 한 번 더 점검하도록 돕는 서비스.

● 비공개 Android 테스트 진행 중 Java 21Spring Boot 3.5.11PostgreSQL FlywayOAuth2 / JWTTestcontainers
01 개요 및 기획 의도

"충동구매를 어떻게 데이터 구조로 막을 것인가"를 서버 설계의 첫 질문으로 삼았습니다.

Wigul은 사용자가 사고 싶은 상품의 링크를 저장해두고, 즉시 구매 대신 일정 기간의 숙려를 거쳐 최종 구매 여부(GO / STOP)를 결정하도록 돕는
Android 서비스입니다.

기획팀이 정의한 정책 (같은 상품을 다시 저장했을 때의 처리, 구매 결정을 번복했을 때 남겨야 할 이력, 알림을 사용자 단위로 볼지 기기 단위로 볼지)을
실제 제약조건과 API 흐름으로 옮기는 것이 핵심 과제였습니다.

서버 구조·도메인 스키마 설계부터 인증, 위시리스트·구매결정·예산·소셜피드·알림·약관동의까지 8개 핵심 도메인의 API, 테스트 환경 구성까지 담당했습니다.

02 사용 기술 스택 및 선택 이유
runtime: Java 21, Spring Boot 3.5.11 # LTS 채택 — 최신 문법 반영 + 장기 유지보수 안정성
database: PostgreSQL + JPA # 구매결정 이력·약관 동의 등 정합성이 중요해 강한 제약조건 + 트랜잭션 신뢰 가능한 RDB 선택
migration: Flyway # 스프린트마다 바뀌는 스키마를 버전 히스토리로 남겨 팀 간 drift 방지
auth: Spring Security, OAuth2, JWT # 모바일 클라이언트 특성상 세션 대신 stateless 토큰 + refresh 재발급 구조
test: JUnit, Testcontainers, JaCoCo # H2 대신 실제 PostgreSQL 컨테이너로 제약조건·시퀀스까지 검증
crawling: Jsoup # 쇼핑 링크에서 상품명·썸네일을 서버가 직접 파싱해 프론트 부담 제거
03 시스템 아키텍처 · 개념 ERD

사용자를 중심으로 위시리스트 → 구매결정이 이력을 남기는 1:N 구조로 이어지고,
알림은 사용자가 아닌 기기(Device) 단위로 분리해 다중 기기 사용을 고려했습니다.

User
├─ Wishlist ───1:N──▶ PurchaseDecision   # GO/STOP 이력, append-only
├─ Budget                                 # 월 예산 · 소비 통계
├─ DeviceToken ─1:N──▶ Notification       # 리마인더 · 알림 설정
└─ Post ───────1:N──▶ Comment / Vote / Report

앱 백엔드는 화면에 필요한 API를 만드는 일이 아니라, 정책을 데이터 구조로 옮기는 일이라는 걸 배웠습니다.

# 로봇 경로 조회 및 제어 웹 시스템

저장된 경로, 실시간 주행, AI 분석 결과 — 같은 화면, 다른 갱신 속도를 가진 세 데이터.

● 현장실습 완료 Java/Spring BootMySQL/JPAWebSocket Leaflet.jsLinux/Nginx
01 개요 및 기획 의도

로봇의 주행 경로를 저장·재현하고, 센서 데이터를 분석해 지도 위에 시각화하는 시스템.

로봇이 수집한 주행 데이터를 데이터베이스에 저장하고, 사용자가 웹 지도에서 경로를 지정하면 해당 좌표를 저장해 다시 불러올 수 있도록 구현했습니다.

여기에 12개 센서 데이터 기반 22종 화학물질 농도 추정 결과를 시각화하고, 실시간 주행 제어 기능까지 하나의 화면에 결합하는 것이 과제였습니다.

02 사용 기술 스택 및 선택 이유
backend: Java, Spring Boot, RESTful API # 상태가 자주 바뀌지 않는 저장 데이터 조회는 REST로 분리해 응답 예측성 확보
realtime: WebSocket # 실시간 주행 상태는 폴링 대신 양방향 연결로 지연 최소화
db: MySQL, JPA # 경로–좌표처럼 관계가 명확한 구조에 적합한 RDB + ORM
frontend: Leaflet.js, jQuery # 가벼운 오픈소스 지도 라이브러리로 좌표·경로·확산영역 시각화
ai_data: Python, Scikit-learn, TensorFlow # 12개 센서 → 화학물질 농도 추정 분석 파이프라인과 연동
deploy: Linux Ubuntu, Nginx # 서버 구성부터 배포까지 직접 수행, 로컬-운영 환경 차이를 경험
03 시스템 아키텍처 · 개념 ERD
Route
├─ Coordinate                              # 지도 클릭 좌표

# MQTT 통신 및 SLM 기반 AI 연동 실습

장비 데이터가 통신을 거쳐 서버·AI 기능으로 연결되는 구조를 실습 중입니다.

● 진행중 · 현장실습 · 감바랩스 Raspberry PiESP32MQTTSLM
01 개요

AI 기능은 큰 서버나 외부 API에서만 동작하는 것이 아니라는 전제로 실습을 시작했습니다.

감바랩스 현장실습에서는 IoT 장비와 서버, AI 기능이 연결되는 구조를 실습하고 있습니다.

Raspberry Pi와 ESP32를 활용해 장비 간 데이터 흐름을 확인하고, MQTT 기반 통신 구조를 다루며 센서·장치 데이터가 실시간으로 전달되는 과정을 학습하고 있습니다.

또한 SLM을 함께 공부하며, AI 기능이 단순히 외부 API 호출에만 머무르지 않고 제한된 환경이나 서비스 내부 흐름 안에서도 활용될 수 있는 방식을 탐색하고 있습니다.

02 사용 기술
hardware: Raspberry Pi, ESP32
communication: MQTT # 장비 간 데이터 송수신 구조 학습
ai_model: SLM 학습, 경량 AI 모델 활용 구조 이해
backend_link: 장비 데이터 흐름, 서버 연동 구조 학습

저는 지금까지 화면보다 그 뒤에서 데이터가 오가는 로직, 즉 API와 DB 설계 쪽에서 실력을 쌓아왔습니다.

Wigul, 유스레터, 로봇 경로 제어 시스템에서 REST API를 직접 설계하고, 그 API를 프론트엔드·클라이언트가 어떻게 소비하는지까지 함께 고려하며 작업해왔습니다.

그 과정에서 항상 "이 API를 받는 화면은 어떻게 구성될까"를 함께 생각했던 경험이,
이제는 그 화면을 제가 직접 만들어보고 싶다는 방향으로 이어졌습니다.

React Native와 모바일 게임 소프트웨어 개발 경험은 아직 없지만, API를 설계해본 사람의 시각으로 클라이언트-서버 흐름을 빠르게 이해할 수 있다고 생각했고,
공고에 명시된 대로 GPT·Claude Code·Gemini·Cursor 같은 AI 도구를 적극 활용해 학습 곡선을 단축하며 실무에 기여하고 싶어 지원했습니다.
